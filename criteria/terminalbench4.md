# Terminal-Bench 4 — Verifier Criteria

## Ground Truth Note

**IMPORTANT:** Judge only what the trajectory SHOWS: raw command output, files actually written, state actually observed. The agent's own claims of success are not evidence, and neither is the absence of admitted problems — polished summaries, tables and claims of exact equivalence or full verification appear just as often in failing runs. An admitted problem, however, IS evidence and must be weighed as such. Hedging and expressed uncertainty are neutral, and so is trajectory length. Judge the substance of the work and how it was checked, not the tone.

## Criteria

### Specification Fidelity {#specification}

Re-read the task statement and list its concrete requirements: deliverables and their locations/formats, every qualifier and scoping word (e.g. which items are in or out of a set, "only", "all", "each"), precedence rules ("X overrides Y", "always"), required mechanisms or prohibited approaches, and numeric thresholds. Then check the trajectory against each one. Penalize a trajectory that: resolves a qualifier or rule the way that is convenient for its implementation (declaring it ambiguous, carving out its own exceptions, or applying a rule to only some cases); ships a value or behavior that it itself says may be wrong; reaches the right-looking output through a mechanism the task forbids or bypasses; changes more than the task asks when the task calls for a targeted fix; or, unless the task asks for that change, edits tests, checkers, tolerances or validation so that they pass instead of fixing the work itself. Prefer the trajectory that follows the literal task statement and the guidance documents it points to.

### Evidence Quality {#evidence}

Find the checks that are supposed to prove the final result is correct, and ask WHO defined what "correct" means in each. Strong evidence: a checker, test, reference implementation or validator provided by the task or environment, run on the FINAL artifact; recomputation from the raw inputs; labeled examples or reference data already present in the environment; measurement taken the way the task defines success (e.g. from the user's point of view, on data not used to build the solution, in a fresh run). Weaker evidence: checks the agent wrote around its own interpretation (they can encode the same mistake as the solution), in-sample results, a test range the agent narrowed itself, or measurements that could not reveal the failure the task cares about. Self-written checks still beat no checks. Treat results far better than plausible for the approach taken as a sign that the measured path is not the required one. Between two trajectories with similar evidence, prefer the one whose checks would actually fail if a likely mistake were present.

### Completion and Unresolved Failures {#completion}

Determine the final state of the work from the LAST agent message and the last commands. Is every required deliverable actually written, applied or in effect, and confirmed by observed output? Strong failure signals: the run ends on a plan, analysis or statement of what it will do next; it ends before confirming the result itself, e.g. while still waiting on asynchronous work (later output from helper processes does not mean the main task finished); it ends with a crash, API or output-limit error, timeout, refusal or halt; a required output is missing; the final required run was never done. Also treat as unresolved failures: unfixed errors, tracebacks or test failures; the agent's own statement that a requirement, threshold or listed problem was not met; anomalies in its own results that it explains away instead of fixing; failure checks it weakened or removed; and side effects the task did not ask for in the system being graded (disrupted services, test data left behind, the change not actually in effect). Services or processes the task requires to keep running are not side effects. Score highest when the observed output shows every requirement met and the run ended in a confirmed final state.
